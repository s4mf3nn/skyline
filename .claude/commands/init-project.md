Initialise ce dépôt, créé depuis le boilerplate, pour un nouveau projet. Argument éventuel : $ARGUMENTS

Garde-fou : si `README.project.md` n'existe pas, le dépôt est déjà initialisé. Dis-le et arrête-toi. Cette commande n'a pas de spec : c'est de la mise en place de l'outillage (mode hors spec).

## 1. Poser les questions

Utilise `AskUserQuestion`, en un ou deux envois groupés, et en français. Ne suppose rien : propose des options, l'utilisateur peut toujours répondre autre chose.

1. **Nom du projet** (kebab-case, ex. `mon-projet`). Reprends l'argument s'il est fourni et valide, sinon propose le nom du dossier courant.
2. **Propriétaire GitHub** : utilisateur, organisation ou `org/equipe`. Propose la valeur de `gh api user -q .login` si `gh` répond.
3. **Phrase sur le produit** : une phrase, pour le README et l'ADR.
4. **Phase d'autonomie de départ** (voir `docs/factory/WORKFLOW.md`, « Roadmap d'autonomie »). Recommande la 1.
   - **1** : 2 agents en parallèle, tu fusionnes toutes les PR (`/land`).
   - **2** : 3 ou 4 agents en parallèle, lecture allégée hors `risk:high`.
   - **3** : 3 ou 4 agents, auto-merge des PR `risk:low`. Prérequis : scénarios cachés sur chaque spec et `gates` vert sur `main`. Même si elle est choisie, l'auto-merge reste désactivé (ligne commentée de `.github/workflows/risk.yml`) tant que tu ne l'actives pas toi-même ; dis-le.
5. **Technologies imposées** : question libre, sans liste fermée. Cite en exemple Hono sur Cloudflare Workers, Neon serverless, Supabase, React, Next.js, React Native, et propose « aucune, tu proposes ». Pour chaque réponse, note son **rôle** (runtime applicatif, framework serveur, framework d'interface, style, base de données ou hébergement de données, authentification, déploiement, autre) et demande si le rôle est ambigu. Une technologie inconnue de toi est consignée telle quelle. Ne déduis jamais une contrainte que l'utilisateur n'a pas posée, hormis Tailwind (voir l'étape 2, point 4).
6. **Type d'application** : API ou service, application web, application mobile, CLI ou bibliothèque. Plusieurs réponses sont possibles (ex. API et application mobile) : demande alors si elles vivent dans ce même dépôt. Ne la redemande pas si les technologies imposées la déterminent (ex. Hono sur Workers : une API) : annonce la déduction dans le récapitulatif.
7. **Base de données** : aucune, ou Postgres (une base par workspace Conductor). Ne pose pas la question si le type d'application l'exclut ou si les technologies imposées la déterminent (ex. Neon : Postgres hébergé ; annonce-le).
8. **Choix de stack** pour `docs/adr/0001-stack.md`, **pour ce qui n'est pas déjà imposé** : framework (HTTP, interface web ou mobile, CLI), validation des entrées, persistance, tests d'interface, découpage d'une feature. Propose des options compatibles avec les technologies imposées, ou « à décider plus tard » (statut `à décider`). Si deux technologies imposées sont incompatibles entre elles ou avec la chaîne d'outils (ex. pilote Postgres TCP sur Workers), expose le conflit et les options à l'utilisateur : ne le contourne pas et ne tranche pas à sa place. Deux technologies imposées de même rôle sont à confirmer.
9. **Zones sensibles du domaine** (authentification, paiement, données personnelles, fichiers envoyés par les utilisateurs...) : liste libre ou « aucune pour l'instant ». Demande aussi s'il y a des **rôles** au-delà de l'utilisateur (modérateur, administrateur, back-office) : leurs features entrent dans les zones sensibles (`**/features/admin/**` par défaut, à adapter au nom choisi).

Récapitule les réponses (technologies imposées avec leur rôle, déductions, implications) et demande confirmation avant d'écrire quoi que ce soit.

## 2. Appliquer

1. Lance : `node scripts/init-factory.mjs <nom> <propriétaire> --phase <1|2|3> --description '<phrase>'`. Mets la phrase entre **guillemets simples**, en remplaçant chaque `'` par `'\''` : entre guillemets doubles, le shell évaluerait les backticks, `$(...)` et `$VAR`. La phrase doit tenir sur une seule ligne. Le script remplace les jetons, fixe la phase, déplace le guide dans `docs/factory/BOILERPLATE.md`, et supprime cette commande ainsi que lui-même. S'il échoue, corrige l'entrée invalide avec l'utilisateur et relance.
2. **Postgres en Docker** (seul mécanisme que les scripts savent créer ; pour un autre mécanisme de ressource de données, voir « Options » du guide, rien à créer ici) : crée `docker-compose.yml` avec le bloc de `docs/factory/BOILERPLATE.md` (section « Options »), décommente le bloc `services` et `env` de `.github/workflows/ci.yml` (sans `API_KEYS` si le projet n'en a pas), et rappelle qu'un script `db:migrate` sera nécessaire.
3. **Application web ou mobile, ou plusieurs applications dans le dépôt** : n'ajoute rien. Sans interface, supprime `docs/factory/UI.md`. Signale ce que SPEC-0000 posera (dont `docs/factory/UI.md` pour une interface) selon la section « Options » du guide : réglages de `tsconfig.json` et de `vitest.config.ts`, script `dev`, et pour plusieurs applications les paquets (ex. `web/`, `mobile/`) avec `pnpm-workspace.yaml`.
4. Complète `docs/adr/0001-stack.md` avec les réponses : date du jour, statut `proposée`, contexte, type d'application, **tableau des technologies** (statut `imposée` pour celles de l'utilisateur, `choisie` pour tes propositions validées, `à décider` sinon ; version épinglée à la dernière stable quand elle n'est pas précisée ; source de la doc via Context7, ou `introuvable`), section **Implications** et conséquences. Si l'application a une interface (web ou mobile), ajoute Tailwind `imposée` (raison : exigence de la factory), et NativeWind `choisie` pour React Native, après avoir vérifié leur version dans Context7 ; sans objet pour une API ou une CLI. Pour chaque application qui s'exécute (API, web, mobile ; CLI si l'utilisateur le veut), ajoute Sentry `imposée` (raison : exigence de la factory, observabilité) avec le SDK de son runtime, vérifié dans Context7 (paquet, version, option qui désactive la collecte automatique de données personnelles) ; sans objet pour une bibliothèque. Ajoute le suivi des erreurs à la ligne « Services tiers » des Implications (`src/shared/monitoring/`). Si le runtime applicatif n'est pas Node, la stratégie de test des Implications prévoit des tests adaptés (ex. Hono : `app.request()`), et le lanceur éventuel est une dépendance à justifier. Plusieurs applications dans le dépôt : un sous-tableau par application.
5. Complète dans `CLAUDE.md` la section « Le projet » en une ou deux phrases ; ne touche pas aux autres sections.
6. Dans `docs/factory/DOMAIN-SECURITY.md`, garde les règles par défaut qui s'appliquent au type d'application et aux fonctions annoncées (authentification par lien ou code, lien d'accès sans compte, secrets émis par le produit, appels sortants vers une adresse fournie par un client, fichiers envoyés, données personnelles) et supprime les autres. Propose les zones de risque du projet dans `docs/factory/DOMAIN-SECURITY.md`, `docs/factory/RISK.md`, `.github/labeler.yml` et `.github/CODEOWNERS` à la fois, et montre le diff avant d'écrire. Cette étape est obligatoire dès qu'une zone sensible a été donnée, que le projet a une authentification, des données personnelles ou une livraison (déploiement, publication sur un store ou un registre de paquets), ou qu'une technologie imposée introduit des secrets ou un accès aux données (ex. Supabase Auth, clés Neon, jetons Cloudflare). Couvre aussi les chemins réels de la stack choisie : dossier des migrations de l'outil retenu, fichiers de configuration de build et de livraison, code partagé. Dépôt à plusieurs applications : garde les globs en `**/` pour qu'ils valent dans chaque paquet. Sinon, dis que les zones par défaut restent en place et rappelle `node scripts/pre-review.mjs zones` après SPEC-0000.
7. **Cache Context7** : pour chaque technologie `imposée` dont la source de doc n'est pas `introuvable`, ajoute à `docs/factory/libs-cache.md` (format du fichier) une entrée courte par API structurante : version épinglée, source nommée avec l'identifiant Context7, date du jour, 1 à 3 lignes. Pas de copie de documentation. Si Context7 est indisponible, dis-le à l'utilisateur et n'écris rien.
8. Ne remplis pas `specs/SPEC-0000-bootstrap/spec.md`, `specs/SPEC-0001-delivery/spec.md` ni leurs tests de contrat à sa place : propose de le faire ensuite avec lui, dans ce même commit initial. Sans livraison ni cible réelle (ex. bibliothèque interne), SPEC-0001 garde ses critères marqués sans objet plutôt que d'être supprimée.

## 3. Finir

1. Lance `git status` et vérifie qu'il ne reste aucun `{{...}}` : `grep -rn "{{[A-Z_]*}}" CLAUDE.md README.md docs .github`.
2. Ne commite ni ne pousse sans demander. Si l'utilisateur accepte, `git add -A && git commit -m "chore(factory): bootstrap software factory"`. Le push sur `main` est une action sortante : confirme-le explicitement, et fais-le **avant** `pnpm install` (voir `docs/factory/BOILERPLATE.md`, étape 4).
3. Termine par la liste de ce qui reste à faire à la main : réglages GitHub (étiquettes, squash-merge, protection de `main`, environnement `production` si l'ADR prévoit une livraison), `.env`, Sentry si l'ADR l'inclut (un projet par application, DSN dans l'environnement `production` et dans `.env` si tu veux le suivi en local, `SENTRY_AUTH_TOKEN` dans l'environnement `production` pour les sourcemaps, jeton utilisateur en lecture seule exporté en `SENTRY_ACCESS_TOKEN` sur ton poste pour le serveur MCP), ajout du dépôt dans Conductor, puis `/plan SPEC-0000` et, dans un autre workspace, `/roadmap <brief>` (cadrage produit et ordre des specs).
